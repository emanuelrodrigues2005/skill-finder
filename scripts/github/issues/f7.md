<!--ISSUE:fix(api): identificar o cliente pelo X-Forwarded-For do ALB-->
## O que entrega

O backend deixa de confiar no header `X-Real-IP`.

Hoje `resolveClientIp` le `X-Real-IP` e cai para `req.ip`; o contrato existe **porque o nginx sobrescreve** o header. O ALB **nao** escreve `X-Real-IP` e **nao** remove headers do cliente — no desenho novo o header chegaria forjado, e `sha256(sal:ip)` (a chave do rate limit e da coluna `client_hash`) passaria a ser escolhida pelo atacante.

A identidade passa a ser `req.ip` com `trust proxy = 1`, que e a ultima entrada do `X-Forwarded-For` — a que o ALB anexa.

## Criterios de aceitacao

- [ ] `grep -rn 'x-real-ip' backend/src` = 0 ocorrencias
- [ ] teste: `X-Real-IP: 1.2.3.4` + `X-Forwarded-For: 9.9.9.9, 200.10.20.30` produz o **mesmo** `client_hash` de uma request sem `X-Real-IP` com o mesmo XFF, e **diferente** de `1.2.3.4`
- [ ] teste: request sem header nenhum (dev direto) produz hash estavel de `req.ip`
- [ ] `bash scripts/dev/verify.sh unit` e `e2e` verdes
- [ ] `openapi.yaml` inalterado

## Verificacao

```bash

grep -rn 'x-real-ip' backend/src || echo 'nenhum X-Real-IP (esperado)'
git diff --exit-code openapi.yaml
```
